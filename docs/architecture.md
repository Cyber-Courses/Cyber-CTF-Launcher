# Architecture

How the launcher is built: where labs run and what runs them, how the code is laid out, and what is
done. For how a lab runs in each place, see [running-labs.md](running-labs.md); for sign-in,
[signing-in.md](signing-in.md).

## Where labs run

A lab describes itself once as an `isoloom.yml` (its machines, networks, services and checks). The launcher uses Isoloom to read that spec and convert it to each target's native files (Compose, Vagrant, Terraform) under the lab's `.isoloom-<n>/` folder (`n`: its instance, see [running-labs.md](running-labs.md#what-says-where-a-lab-is)), then runs them in one of three modes:

| Mode       | What runs the lab                                                                                                                                                                                                              |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Local**  | Docker on the player's machine (Docker Compose), or VMs through Vagrant on any local hypervisor (VirtualBox, VMware Desktop, Hyper-V, Parallels, libvirt, QEMU, UTM). Containers can also run inside a local VM (`docker-vm`). |
| **Server** | The player's own **Proxmox** or **VMware ESXi** server, through Vagrant or Terraform.                                                                                                                                          |
| **Cloud**  | The player's own **AWS, Azure, GCP, DigitalOcean, Linode or Oracle Cloud** account, through Terraform with that provider's CLI credentials.                                                                                    |

### Lab engine

The [Isothrum runner](https://github.com/Isothrum/isothrum) runs every lab with machines, in every mode above: it executes the versioned run manifest Isoloom writes beside the generated files (local Docker, a container lab in a local VM (`docker-vm`), local VMs, Proxmox and ESXi servers, and `cloud-docker` / `cloud-vm` in a cloud account). There is no other engine to choose: cloud-services labs (managed cloud services, no machines) run through it too, the lab's own Terraform module applied by the runner in the player's account (`runtime/cloud_services.rs`).

**Proven vs. generated.** Local labs (Docker, Docker in a VM, VMs) and server labs (Proxmox and ESXi) are proven by real runs, and so are cloud labs on **AWS**: the integration tests' AWS tier runs `cloud-docker` and `cloud-vm` labs end to end in a real account ([testing/integration.md](testing/integration.md)). On the other clouds the Terraform Isoloom generates passes the cloud's official validator but hasn't been run end to end on a paid account yet.

## The code

- **UI:** Next.js as a **static export** (`output: "export"`) served by Tauri. There is no Next server, so no API routes, SSR or middleware. The UI only calls typed Rust commands ([`src/lib/tauri/`](../src/lib/tauri/), one module per area).
  - [`src/features/`](../src/features/): one folder per page with its parts and hooks: `labs` (catalogue, lab page, deployment steps, network diagram), `machine` (Machine page and the setup steps), `servers`, `cloud`, `settings`, `home`, `onboarding`, `account`, and `app` (what shows over every screen: the website launch prompt, the quit guard).
  - [`src/components/ui/`](../src/components/ui/): shared building blocks (Button, Panel, RadioRow, Segmented, ChoiceCard, StatusPill, LogConsole…); [`src/components/`](../src/components/) holds the app shell.
  - [`src/lib/`](../src/lib/): data access ([`tauri/`](../src/lib/tauri/)), per-machine settings, formatting ([`format.ts`](../src/lib/format.ts)) and small helpers.
- **Core (Rust, [`src-tauri/`](../src-tauri/)):** everything privileged. Processes are spawned without a shell, lab ids are validated, and the UI never passes paths or command lines.
  - [`account/`](../src-tauri/src/account/): Cyber Auth sign-in (`auth.rs`: authorization code + PKCE through the system browser, loopback redirect on `127.0.0.1:47290-47292/callback`, or a code entered on another device (`auth/device.rs`); tokens in the OS keychain, refreshed automatically, never in the webview; see [Signing in](signing-in.md)), CyberBackend GraphQL with the token attached on the Rust side (`api.rs`), and the agent that links the launcher to the website (`agent.rs`: a claimed launch; `agent/identity.rs`, `agent/registration.rs`, `agent/confirm.rs`; and `colocation.rs`).
  - [`labs.rs`](../src-tauri/src/labs.rs): `lab_launch` calls `startLab`, then downloads `CyberCTF/*` at the pinned commit (full SHA only; archive paths checked), and starts the lab with `CTF_API_URL` and `CTF_LAUNCH_TOKEN`. The lab's `evidence` service exchanges the token for this player's evidence. A lab imported from a folder (`lab_launch_local`) is copied in as `local-<name>` and started without the backend; `labs/imported.rs` lists the imported labs installed here for their pages, with what each one's `.ctf/` folder defines (`labs/ctf.rs`).
  - [`machine/`](../src-tauri/src/machine/): what this machine can run (`system/`: Docker engines, Vagrant, hypervisors, package manager), the setup self-tests (`selftest/`), the workloads/storage the Machine page shows (`workloads/`, `storage.rs`) and one-click dependency installs (`tools/`).
  - [`platform/`](../src-tauri/src/platform/): running tools without a shell (`exec/`, with the VM self-test's Hyper-V elevation in `exec/elevate.rs`), files only this user can read (`private_fs.rs`), whole-file writes (`atomic_file.rs`), the OS keychain the session and the servers' secrets are kept in (`keychain.rs`), HTTP clients with timeouts and a download size cap (`http.rs`), the PATH a GUI launch is missing (`env_path.rs`), the corporate proxy handed to tools (`proxy.rs`), secrets kept out of logs (`redact.rs`), the administrator's policy (`policy.rs`), tools' answers kept a while (`remembered.rs`), a console Ctrl+C on Windows (`console.rs`), the Store build's files moved out of its virtualized folder (`msix_data.rs`), the root scripts' checked downloads and pinned signing keys (`root_script.rs`), symlinks kept only inside a copied tree (`tree_link.rs`), a panic in a future caught where it is polled (`unwind.rs`), every call into libc and Win32 (`sys/`, the one place `unsafe` is allowed), and the service endpoints (`config.rs`).
  - [`runtime/`](../src-tauri/src/runtime/): lab lifecycle, with logs streamed to the UI over a Tauri channel
    - `lab/`: the launcher's one door to Isoloom's spec and generators (`isoloom-spec`, `isoloom-targets` are used nowhere else; the types others need are re-exported from it): the target's files (Compose, Vagrant, Terraform) are generated from the lab's `isoloom.yml` right before they run, then the launcher's own overrides applied (`overrides.rs`); Isoloom's paths and names (`names.rs`); the variables of Isoloom's Terraform modules from the player's hosts and accounts (`vars.rs`); each lab's instance numbering (`instances.rs`); where and how a lab can run (`run_options.rs`) and each launch path's maturity from Isoloom's tier evidence (`tiers.rs`)
    - `isothrum.rs` + `isothrum/`: the Isothrum runner (`isothrum-runner`), the one lab engine: the launcher hands it every lab with machines, wherever it runs (here, on a server, in a cloud account), and it executes the run manifest Isoloom wrote, whose types (`isoloom-manifest`) only this module reads; its runs live under the app data folder's `runs/`, never in the lab folder
    - `deploy_log.rs`: the launcher's own deploy-log lines that the lab page files under a step (fetching and placing the lab, readying this machine), each built from the start the page reads them by (generated into `src/lib/tauri/generated/DeployLog.ts`)
    - `launch.rs`, `lifecycle.rs`, `status.rs`: start, park/resume and stop, and what is running where; whether something of a lab is still up (an update, a re-import or a start elsewhere waits for it to stop) is read from the runner's record of its run, wherever it runs
    - `reaper.rs`: the auto-stop of cloud labs past their stop time, through the runner, after handing it the deployments the launcher's own Terraform left
    - `docker/`: reads only, never starts or stops anything (the runner does): a running container lab's reachable URL here, the address blocks Docker's networks hold, the lab-check result types, and the Compose project name and the names an older version's attack box carried; Docker's address-pool overlap said as what to do (`pool_overlap.rs`)
    - `server/`, `proxmox.rs`: the player's own servers (ESXi, Proxmox) and cloud accounts (AWS, Azure, GCP, DigitalOcean, Linode, OCI) labs run on; `server_selftest/` checks a server or account before the first lab
    - `cloud_services.rs`: cloud-services labs, run by the runner in the player's account; the launcher keeps the policy (the account, the budget, this machine's IP for an allow-list)
    - `terraform/`: reads only: the states the launcher's own Terraform left before the runner (for their hand-over to it) and the Terraform plugin cache the Storage page cleans
    - `providers.rs`: every place a lab's VMs run and its name. Local hypervisors (Vagrant providers): VirtualBox, VMware Desktop, Hyper-V, Parallels, libvirt, QEMU, UTM. Servers: VMware ESXi, Proxmox. Clouds: AWS, Azure, GCP, DigitalOcean, Linode, OCI.
    - `attack_machine.rs` + `attack_machine/`: the attack box, a machine the launcher adds to the lab through its overlay (`lab/overlay.rs`), at the seat the lab declares for the player or as `attackbox` on its first network: a container among a container lab's, a Kali VM among a VM lab's
  - [`app/deploy_worker/`](../src-tauri/src/app/deploy_worker/): launches, resumes, parks and provisioning runs in a detached worker process (`cyberctf-desktop deploy --job <file>`), so quitting the app never cuts a deploy short. The per-lab file lock that keeps the app and the workers from running two operations on one lab at once is the runtime's (`runtime/inflight/lock.rs`): the app depends on the runtime and the labs, never the other way round (the stop command hands `labs::stop_lab` the ending of the lab's workers, the `lab_status` command masks a lab whose last launch failed in its worker, and `app/operations.rs` merges the workers' jobs with the runtime's operations for the sidebar).
  - `terminal.rs`: the in-app attack box shell (a PTY streamed to xterm.js); `screen.rs` + `screen/`: a lab machine's screen window, its graphical console through the runner, drawn by the vendored noVNC through the window's loopback WebSocket bridge (`bridge.rs`, `ws.rs`), or a Remote Desktop opened in the system's client (`rdp.rs`); `shared_folder.rs`: the folder shared with the attack box.
  - `cloud.rs`: cloud account sign-in through each provider's CLI; `error.rs`: crate-wide errors.
  - [`app/`](../src-tauri/src/app/): the app shell (windows, menu, quitting, the log file); [`commands.rs`](../src-tauri/src/commands.rs): the commands the webview invokes.

The runtime layer knows nothing about CTFs: a lab is a directory with an `isoloom.yml` (its machines, networks, services and checks). It names none of the layers above it (`labs`, `account`, `machine`, `cloud`, `commands`, `app`), and those domain layers name neither the app shell nor the commands; what a layer needs from above is handed in: the rule for which repositories a lab's spec may be fetched from (`runtime::lab::Source`, `labs::source`), what to end before a stop (`runtime::stop_lab`'s `end_first`: the deploy workers, the website's co-location check), whether a deploy worker is busy (Storage's clean-up), and a start's downloads, which `labs` records for Storage around it (`runtime::downloads`). A source scan (`testing/source_scan.rs`) holds every layer to that.

Labs live in `<app data>/labs/<lab id>/`.

### Platform notes

A VM lab runs natively only where its boxes exist for the host architecture. On Apple Silicon, ARM boxes run natively on UTM/QEMU (Apple Hypervisor). x86-only boxes such as pfSense run there only under QEMU emulation, which is several times slower; heavy x86 labs should use a remote x86 host (ESXi, Proxmox).

Hyper-V only takes management commands from an administrator (or a member of "Hyper-V Administrators"), and Vagrant's Hyper-V provider refuses to run otherwise. A lab's Vagrant runs inside the Isothrum runner, which elevates its Hyper-V commands itself; the launcher only puts the runner's declined or failed elevation into words (`runtime/isothrum/errors.rs`). The one Vagrantfile the launcher runs itself is the VM self-test's: on Windows its commands run through a generated, hidden Windows PowerShell script ([`platform/exec/elevate.rs`](../src-tauri/src/platform/exec/elevate.rs)); when the launcher itself may not manage Hyper-V, Windows first asks for administrator rights (a UAC prompt, raised for the app's window). Status reads are never elevated, and Vagrant refuses even those without the rights: so the Machine report shows Hyper-V as not ready for an account that may not manage it, and Settings > Labs > Hypervisor offers **Allow my account**, which adds the account to "Hyper-V Administrators" (one UAC prompt; it takes effect at the next Windows sign-in).

- Prompts: one per batch of the self-test's Vagrant commands. The VM self-test asks twice (boot and run a command, then delete the test VM), three times when it first deletes a test VM left from an earlier run. Started as administrator (or as a Hyper-V administrator), the launcher asks nothing. A lab's own start, provisioning run, pause or shutdown, resume and stop, and adding or taking out the attack box, ask as the runner does.
- Output streams as usual: the script writes it to a log the launcher follows. The environment the commands need goes through a file in the batch's own temp folder, read and deleted by the script, never on a command line.
- Vagrant's questions: on Windows, Vagrant waits forever for an answer even with no one to give it. The script picks a virtual switch ("Default Switch", else an external one, else the first) unless `ISOLOOM_HYPERV_SWITCH` already names one, and passes it as `ISOLOOM_HYPERV_SWITCH`, which the self-test's Vagrantfile attaches to. A lab's Isoloom Vagrantfile reads the same variable from the environment the runner starts Vagrant with (a setting of the lab's run), and takes the Default Switch without it. If Vagrant asks anyway, the batch is stopped with a message saying so.
- Stopping: cancelling the test or the launcher exiting ends the batch and every process it started; a batch running for more than 6 hours is ended too. Declining the UAC prompt fails the test with a plain message.

## What is done

- [x] System check, Docker/VM runtimes, provider detection
- [x] Login: system browser + PKCE against cyberauth.co, loopback redirect, tokens in the OS keychain
- [x] Login with a code on another device (device authorization grant), once cyber-auth enables it for the launcher's client
- [x] Lab catalogue from [CyberBackend](https://github.com/Cyber-Courses/CyberBackend); launch = `startLab`, download at the pinned commit, run with the launch token
- [x] Servers (ESXi/Proxmox, credentials in the keychain) and cloud accounts (AWS, Azure, GCP, DigitalOcean, Linode, OCI)
- [x] Attack box on the lab network (Cyber CTF image on Docker Hub, built by the attack-box workflow)
- [x] VM lab provisioning from the lab's `isoloom.yml` (through Isoloom), re-runnable per machine from the lab page
- [x] Signed updates: the in-app updater installs only updates signed with the launcher's key (minisign), from `latest.json` on GitHub Releases
- [x] Signed and notarized macOS app (Developer ID)
- [ ] Authenticode-signed Windows installers: up to 1.8.9 they are unsigned; from the next release `release.yml` refuses a tag build without the Azure Artifact Signing secrets
